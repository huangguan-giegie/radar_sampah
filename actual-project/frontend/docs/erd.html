What the picture cannot show

Six columns, one report

Every qty_* column is nullable and null means "not seen", never "zero" — nobody counted an absence. A named constraint keeps a report from being empty: CHECK (num_nonnulls(qty_plastic, …, qty_other) >= 1).

The blue rows hold an address, not an image

There is no photos table and no image bytes in the database. POST /uploads/photos writes the file to object storage, strips its EXIF, and returns a URL; photo_url keeps that address and photo_stripped records that the location tag really came off. Two consequences: a file deleted in storage leaves a link to nothing and the database never notices, and orphaned uploads have to be swept by hand — no foreign key will do it.

Why category and quantity survive

They are now derived — the highest-weighted non-null qty_* column and its value — kept so the published severity rule and the existing list views keep working while the six columns are introduced. They can be dropped once the record screen is multi-select.

The dashed line is a read

A beach's litter composition is not stored. GET /beaches/:id takes that beach's most recent Counted report, lists its non-null categories by weight, and returns a compositionSource naming that report and its date. Both are null until the beach has a Counted report.

Not columns on beaches

severity band insufficientData validReports lastReportedAt freshnessKind composition compositionSource species ecologicalNote all appear in the JSON but none are stored — the backend computes each one per request.

species_id is nullable on purpose

Only real species with a scientific name reach dim_species. Habitats ("Mangrove forest") and group names ("Coastal birds") have none, so they live on area_species alone. A CHECK ties this to kind: (kind = 'species') = (species_id IS NOT NULL).

Indexes the contract requires

reports (beach_id, status, created_at) for the severity window, and reports (reporter_id, beach_id, created_at) for the duplicate check. A third, photos (created_at) WHERE report_id IS NULL, finds uploads no report ever claimed — they are swept after 24 hours.

Two id conventions in one schema

Every id the contract shows by example is a prefixed string — u_01H…, r_01H…, ph_01H… — so those columns must be text. But the two tables that ship real DDL declare uuid primary keys. Both cannot be right. Pick one before writing the migration; a uuid column will not accept u_01H….

Coordinates share a table with everything else

reports.lat / lng are written only for a GPS capture, rounded to 3 decimals on the device. A SELECT * will carry them out. Exclude both columns in the serialiser, not per endpoint.
