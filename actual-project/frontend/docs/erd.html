Database schema

Everything the backend needs to create. The column names tell you half the story — the constraints, the derived columns and the two privacy guarantees are the other half, and they are written next to the table they govern.

PK primary key FK foreign key ENUM fixed values NULL nullable PRIVATE never in a response DERIVED computed from other columns

How they connect

Solid arrows are foreign keys. The one dashed arrow is a read, not a key: a beach's litter composition is taken from its most recent Counted report, so nothing aggregates and nothing is stored twice.

foreign key derived read — the latest Counted report becomes the beach's composition
users
One row per participant. Deliberately holds no personal data.
id PK
uuid / ulid
Internal identifier. Never shown to anyone.
participant_id
text, unique
The 4-digit number the app shows, e.g. 1637. Assign it randomly, not from a sequence — a sequence leaks how many participants exist and who joined first.
role ENUM
volunteer · moderator
Iteration 1 only ever issues volunteer. moderator is reserved for the later review flow — create the value, leave it unused.
created_at
timestamptz
When the number was issued.

No name, no email, no phone, no password column — by decision, not oversight. A report is attributed to a number and nothing else, so there is no personal data to protect, export or delete.

The number is the credential. Anyone who types 1637 sees participant 1637's records. That is acceptable for an MVP running on synthetic data. Before this ever holds real public submissions it needs a secret alongside the number.

beaches
The four monitored beaches. Seed data — no create, update or delete endpoints in Iteration 1.

text slug
morib, remis, kelanang, bagan. Slugs, not numbers — they appear in URLs.

District line under the name, e.g. Banting, Selangor.

Where the map marker sits. This is the beach's own position and is public — do not confuse it with the reporter's coordinates on reports, which are not.

Which icon the biodiversity map marker draws. It is the glyph of this beach's first card — store it, or derive it from area_species ordered by sort_order.

A CSS background value used as the no-photo placeholder. Already written in the seed data — store and return it verbatim.
created_at
timestamptz
Bookkeeping.

No composition column. GET /beaches/:id builds the litter breakdown at read time from the beach's latest Counted report — see reports below.

dim_threat
IUCN conservation categories. A dictionary table, required by DMP §6.
threat_id PK
smallint
Small fixed set — nine rows, seeded once.
threat_name
text, unique
Critically Endangered, Endangered, Vulnerable, Near Threatened, Least Concern, Data Deficient, Not Evaluated, and the two extinct categories.

Kept as its own table rather than a text column so the category can never be misspelled and so a species can be re-graded in one place.

One row per real species. Only rows that have a scientific name belong here.
species_id PK
bigint
Surrogate key.
scientific_name
text, unique
The natural key — upsert on this column, so importing the same dataset twice does not duplicate rows.
common_name NULL
text
English name shown on the card when there is one.

→ dim_threat
Null means not yet graded. Do not substitute Least Concern for unknown.

turtle · bird · mangrove

Which of the six built-in icons the app draws. The app has exactly these six shapes and no image fallback, so a value outside the list renders nothing.
picture_url NULL
text
Optional real photograph. The glyph is always drawn as the fallback.
created_at
timestamptz
Bookkeeping.

Habitats and group names do not go here. "Mangrove forest" and "Coastal birds" have no scientific name, so they live on area_species with a null species_id.

area_species
Which cards a beach's biodiversity section shows, in order. One beach has many rows; one species can appear at many beaches.
id PK
bigint
Surrogate key.
area_id FK
→ beaches.id
The beach this card belongs to. Unique together with display_name so the same card cannot be seeded twice.

→ dim_species
Null for habitats and group names. Set only when the card is one real species.

Must agree with species_id: species requires it, the other two require it to be null.
display_name
text
The card heading, e.g. Green sea turtle or Mangrove forest.
text

The one-sentence description under the heading.
sort_order

Display order within the beach. Also decides primary_species_glyph.

Whether a person wrote the row or a dataset import created it.
source_dataset ENUM
FishBase · OBIS
other · pending
Where this claim comes from. The app prints an amber SOURCE PENDING badge on any card whose value is pending — so an unsourced card is visibly unsourced rather than quietly wrong.
source_citation
text
The attribution line. FishBase and OBIS are CC BY-NC: the citation must be shown, and the data must not be used commercially.
source_url NULL
text
Link to the record.

When the dataset was read. Required by the licences.

smallint 0–100
Epic 5's probability figure. Null hides the bar entirely.
likelihood_basis NULL
text
Plain-language reason for the number. Required whenever the percentage is set — a bare percentage with no stated basis reads as measured fact.

Never merge likelihood into the litter severity score. They answer different questions and are computed from unrelated inputs; a single blended number would be defensible as neither.

reports
The core table. One row per submitted observation.
id PK
uuid / ulid
Returned to the app and used in every later edit or delete.
reporter_id FK
→ users.id
Who submitted it. A number, never a name.
beach_id FK
→ beaches.id
Which beach it belongs to.
photo_id FK NULL
→ photos.id
The evidence photo. Null only for a report saved before its upload finished.

gps · manual
Whether the beach was resolved from the phone's position or picked from the list.

Small · Medium
Large · Very Large
How much plastic was seen. Null means "not seen", not "zero" — the reporter never counted an absence, so a null must never be rendered as 0.
qty_fishing_gear ENUM NULL
same four bands
Nets, lines, traps. The heaviest-weighted category in the severity rule.
qty_glass ENUM NULL
same four bands
Bottles and fragments.
qty_metal ENUM NULL
same four bands
Cans, scrap.
qty_paper ENUM NULL
same four bands
Cardboard, packaging.
qty_other ENUM NULL
same four bands
Anything that fits none of the five above.
category DERIVED
6 categories
The highest-weighted non-null qty_* column. Kept so existing list views and the severity rule keep working unchanged.
quantity DERIVED
4 bands
That column's own value.
lat, lng PRIVATE NULL
numeric(9,3)
Written only when location_source = gps, and rounded to 3 decimals (~110 m) by the app before it is ever sent. Exclude these two columns explicitly in the serialiser — not by remembering to omit them per endpoint.
status ENUM
Counted · Duplicate
Incomplete
Only Counted rows feed the severity score and the composition read.
status_note NULL
text
One sentence explaining a non-Counted status, shown to the reporter.
created_at, updated_at
timestamptz
Bookkeeping.
deleted_at NULL
timestamptz
Soft delete. A deleted report leaves the counts and stops appearing.

At least one category column must be non-null. CHECK (num_nonnulls(qty_plastic, qty_fishing_gear, qty_glass, qty_metal, qty_paper, qty_other) >= 1) — a report that records nothing is not a report.

The beach's litter composition is read from here. GET /beaches/:id takes the beach's most recent Counted report, lists its non-null categories ordered by weight, and returns them with a compositionSource naming that report and its date. Both fields are null when the beach has no Counted report yet. Nothing is averaged and nothing is cached.

Open decision — severity with more than one category. The published rule in §3 takes one category and one quantity. Until the multi-category formula is agreed (max, sum or mean), severity runs on the derived category / quantity pair, which reproduces today's single-category behaviour exactly.

photos
Evidence images. The bytes live in the database, not on disk.
id PK
uuid / ulid
Also the public path: GET /photos/:id streams the bytes back.
data
bytea
The image itself. Storing it in the database keeps backup and deletion to one system — the DMP's retention rule applies to one place, not two.
mime ENUM
image/jpeg · image/png
Validate on upload; do not trust the filename.
bytes
integer
Size after processing. Reject over 8 MB before writing.
metadata_stripped
boolean
EXIF must be removed on the server, including the GPS block a phone camera writes. Record that it happened; a photo with this false should never be served.
report_id FK NULL
→ reports.id
Back-link, filled when the report is created. Null rows are uploads that were never submitted — sweep them.
created_at
timestamptz
Bookkeeping.

Photos are public. Anyone with the id can fetch the image, by decision. That is exactly why the EXIF strip is mandatory rather than advisory.

Two things that are not tables

Severity bands

The four bands and the category weights are published by GET /scoring-method and currently live in the frontend's scoring.ts. If the backend needs to compute severity too, move them into a table so there is one copy, not two that can drift.

Composition

Not stored anywhere. It is a read over the latest Counted report, which is why changing a report changes what the biodiversity page shows immediately.
